# Architecture

Occipital is how agents' work reaches and renders in the CortexKit phone and desktop apps. It is two things at once:

- **A daemon module, `ck-occipital`** (`crates/occipital-module`), the reserved `occipital` module of the subconscious daemon (subc). It is the one module the apps use for a chat: it reads every session from the llm-runner hosting it, composes the pages and live text the apps draw, forwards sends, Stop and uploads, keeps the display data tool providers write for each call, keeps the notices modules send agents, and relays the person's commands to the modules that own them. It also serves the reply teaching, the part of a head's system prompt that teaches the interface tags.
- **The libraries:** the interface language (`crates/occipital-lang`, published as `cortexkit-occipital-lang`), its C binding packaged for iOS (`crates/occipital-ffi`, wrapped in Swift as `OccipitalKit`) and the mention finder for links and chips (`crates/occipital-refs`, published as `cortexkit-occipital-refs`), which the apps embed, so a reply, a tool row, a link or a chip is drawn the same way on the phone, on the desktop and in the module; and the tool template contract and checker (`crates/occipital-registry`, published as `cortexkit-occipital-registry`), which tool providers run in their CI.

`STRUCTURE.md` has the directory map and where to add new code. The module guide, `crates/occipital-module/README.md`, lists every operation.

## Terms

- **Runner:** a module implementing the llm-runner contract, which hosts sessions and stores their messages. Broca is one; Thalamus's `thalamus-harness` hosts OpenCode 2, Claude Code and Pi sessions, and `thalamus-pi` hosts Pi sessions until they move. Occipital talks to runners only through the published contract (`cortexkit-role-llm-runner`).
- **Head, worker:** a head is an agent a person works with; a worker is one an agent started. Both are sessions on a runner, and the apps read both.
- **Harness:** the shape of a session's stored messages (`broca`, `opencode2`, `claude-code`, `pi`). A request names it; a request without one is read as Broca.
- **Page:** a window of a chat's messages as app rows, newest first or before an ordinal. Every page carries a **version**, `history:<n>:incarnation:<id>` (just `history:<n>` when the runner names no log), taken from the runner's history counter and log identity. The apps cache pages by version and reload a chat whose version changes.
- **Claim:** what an app sends back to resume a chat it holds: the version it holds, the oldest and newest messages it has, and, for an app that asks for it, the `heldCopy` its last newest page or claim answer named. The answer is `matched` (with any new rows), `diverged`, `cursor_expired` (with the whole page again) or `outside_window`. A newest-page read that names an unchanged activity token, or a claim on a chat still empty, is answered `unchanged`.
- **Live text:** the words of a reply as the model writes them, before the runner stores it. A **display watch** streams them; the stored row replaces them once it lands.
- **Tool call identity:** each tool part carries `callKey` (the runner's key for the call, unique across that runner) and `schemaPin` (which version of the tool ran: a `tp1` pin names the tool's schema digest and semantics, a `tp2` pin its schema digest and major version, so a compatible update keeps it). A call moved to another runner with its history keeps its key, and the runner names the one that minted it as `call_carrier`.
- **View, template, record, completion, detail:** a tool provider's **view** of a tool version says how its calls draw: an `occipital.template/1` **template** for the row and the page, plus the shape of what it writes. For each call the provider writes a **record** (drawn on the row), a **completion** and a **detail** (drawn on the page).
- **Notice:** a module's message to an agent, such as a reminder or a status line. It reaches the agent either as its own message, which is a chat row like any other, or **riding** the next tool result, which makes no row.
- **Command:** something a module lets the person do from the apps directly, without asking a model, such as Magic Context's flush. A **preview** says what it would do now, in **facts** (a label with a number and unit, or a fixed state); a **run** does it.
- **Reply stamp:** the interface dialect and catalog digest a runner records on a head's reply, so the apps know which tags it may hold. Replies use catalog 1.0; tool templates use tool catalog 1.1.

## How the apps reach Occipital

The phone reaches the computer through Callosum, the federation module: every phone call arrives on a route stamped `reserved:callosum` with the device it came from. The desktop app connects to the daemon directly. Admission reads only what the daemon attests on the route: the route's principal, the device class Callosum stamps (only `phone`, the phone simulator's `sim` and `app`, a paired client such as the desktop reaching this computer from another one, are admitted, never a paired computer, which relays its agents and modules rather than the person), and the operator-app stamp that names the desktop. While the desktop is in development, a plain local caller is admitted too. Everything else is refused before the request is read further.

Occipital in turn calls runners, Entorhinal, tool providers and command modules as `reserved:occipital`, proved by its launch nonce. A runner admits Occipital's reads and sends by the session's plan, which prefrontal writes: Occipital is listed as a reader and as a sender, with the send modes the plan grants.

## Reading a chat

1. **Find the session.** Entorhinal maps the app's session id and harness to the runner hosting it. A harness recorded on a runner that doesn't host it is refused, never read in another harness's shape. A Broca session Entorhinal has no record of, one a module started for its own work such as Magic Context's dreamer runs, is read straight from Broca, which finds it by harness and session and decides whether Occipital may read it. Broca answers a session it never wrote as an empty one (log identity `unwritten`); without an Entorhinal record that is no session at all, such as another runner's session id named under the wrong harness, so it is refused `session_unknown`. Such a session is read only: no `sender`, no command subject, and sends, Stop and uploads refuse it, because they resolve through Entorhinal.
2. **Read the runner.** `session.head` gives the history counter, log identity, run state and send grant. `session.read` serves every page (newest and older, by ordinal range) and every exact read, with display facts (the app's message ids, tool times, call identity, creation and finish times, notices, message marks, host-written parts); raw `session.history` only finds the ordinal of a message that an app's claim (see Terms) or exact read names, and its rows are never shown.
3. **Build rows.** `crates/occipital-app-reader` turns stored messages into app rows. Broca's messages are decoded directly; OpenCode 2, Claude Code and Pi messages go through the runner contract's own display projections first, so every harness reaches the apps in one row shape. A Broca tool result, which Broca stores in its own envelope, reads as the text the model was given, through the runner contract's conversion of that envelope (`owned_broca::tool_output`); a picture or document a tool returned is listed apart, under the call's `media` on an exact read. Occipital builds rows from the runner's raw entries, never from text a runner pre-renders. A stored message that can't be read at all becomes an `unreadable` placeholder row in its place; a single part that can't be shown becomes an `unreadable` part, and the rest of the message reads. Either way Occipital logs why. Text a host wrote into a person's message (Claude Code's `[Request interrupted by user]`), which the runner names in the read's `host_parts`, becomes an `injected` part marked `host` and stays out of the row's text, so it is never drawn as the person's words. OpenCode 2's own `synthetic` messages, which the runner contract counts as host text whole, become a person's row holding only such a part, with a code when the read's `host_parts` names one. A message the person sends while a Claude Code turn runs is stored by Claude Code as a `system` message inside two fixed sentences of its own; when the read's `host_frame` fact names that wrapper and the stored text matches it exactly, the contract's projection splits it, and the row is the person's, their words its text and the two sentences host parts carrying the frame's code. A host part in a reply is the host's own bookkeeping (the empty reasoning blocks that record a fallback model) and is left out of the row; when the runner knows another model answered in place of the one asked for, its `model_fallback` fact reaches the row as `modelFallback`, naming both, and why when the runner recorded it (`by`, `category`, `cause`). An entry the runner wrote itself, such as the empty reply it records when a host saved none for a finished step, carries the read's `runner_entry` fact, which reaches the row as `runnerEntry` with its code.
4. **Answer.** The reply carries the session facts (model, last run, send grant, service tier, history intake while a moved chat's older messages are still arriving, and a host the runner has lost track of) at its top level, never inside a page, so a reply whose page is trimmed to fit still carries them. The model is the head's next-send selection; when it names no reasoning effort, `defaultVariant` names the one the runner sends by default, kept apart from `variant` so an app that sends the selection back never makes the default a choice.

An agent given prefrontal's `say` tool talks to the person through it, and each call's `text` is a message, not a tool call (`occipital-app-reader/src/say.rs`). The stored call doesn't name its provider, so row building marks each call named `say` with its whole text, and the module settles the marks once rows are built (`settle_say` in `app_reader/broca.rs`). It reads the session's plan view, only for rows that hold such a call, and keeps the answer per session for a minute (`app_reader/message_tool.rs`). Where the plan gives the agent prefrontal's `say`, an answered call becomes a `message` part in its place, one still running is left out, and one that failed stays a tool card. Elsewhere every such call is a tool card. While the plan can't be read, a page holding such a call takes the answer kept last, however old; with none kept it is refused `provider_unavailable`, never served with its calls guessed, since settling them later wouldn't move the page's version. The part takes its text from the call's input, and the message it answers, its verified quote, media and alert from prefrontal's message record (`display.write` with `kind: "message"`, which only prefrontal may write), read from the display store while the row is built (`display/call_pins.rs`). `session.details` names the tool as `messageTool` to an app that asks, from the same kept answer, so the apps offer their Simple view, which shows only the person's messages and the agent's `say` messages, only there.

A page's version moves only when the runner's history counter or log identity does. A change in how Occipital renders rows doesn't move it, so apps holding a chat keep their copy until it reloads.

An append doesn't move the version either, yet a row can change in place: Broca stores a step before its calls run, and a call's row gains its result when the result lands as a later entry. So a claim at an unchanged version is also checked against the copy its claimant was served, kept per chat in memory (`claim.rs`), and a held row that changed answers `diverged` with a resync from that row. The kept copies are shared by every reader of the chat, so to an app that asks (`acceptHeldCopy: true`) each newest page and claim answer names the copy it served as `heldCopy` (a digest of its version and rows, so equal copies share a name), and a claim that sends it back is checked against exactly that copy while it is kept. A page back records no copy and names none. A claim without a name, or naming a copy no longer kept, falls back to the oldest copy ending at its `sinceMessageId` that also contains its oldest held message. A `matched` answer names the oldest row actually compared in `vouchedFromMessageId`; it does not certify rows below that boundary. After a restart no copy is kept: an equal version from a runner that versions its history can still match, but its vouch starts no earlier than the oldest currently visible row in the claimed range.

### The Simple view

The apps' Simple view shows the person's messages, the agent's `say` messages, the asks it files and the person's answers to them, and in a busy head that is a few messages in hundreds. So a page or watch that names `view: "simple"` is served from the chat filtered for it (`occipital-app-reader/src/simple.rs`): each row is one the rule admits, trimmed to the parts the view draws, with the full history's ordinals and message ids. Whether a wake holds an answer to an ask comes from its wake record. A Simple page's version is the full one with the rule's number added (`:simple:2`), so a full claim never matches it and a changed rule reloads only Simple copies; its claims are checked against the Simple copies kept apart from the full ones, so a turn that newly joins the view inside a held range answers `diverged`. A read goes back through the history until it holds its rows, reaches the start, or has read a bound of messages, and says where it stopped (`nextBeforeOrdinal`), so a page can hold fewer rows than asked, or none. Each chat's Simple rows are kept between reads with the range they were found in (`simple/tails.rs`), so a busy chat's watch reads only its newest messages again; a record written for a call one of them draws drops them. A read of one message by position reads the full stream, and `view` is refused there.

## Live text and tool frames

Each open chat has one subscription to its runner's live events, shared by every app watching it (`app_reader/display_hub.rs`). Text arrives in a ring that batches deltas for 300 ms; a watch or read that starts mid-reply first gets the text written so far. A reader that opts in with `acceptToolFrames` also gets a frame for each call as it starts and ends, matched to the stored part by `callId`; a run that ends with calls still running marks them unanswered. A runner whose host names a message only when it stores it (Pi, `live_ids`) streams the message's words under a runner-minted `live_id`. Occipital keeps that key as `messageID` for every frame about the message in that run, including its calls' frames, which the runner names by the stored `mid`. So an app holds the step as one reply until the stored copy replaces it. A step whose words weren't shown live keeps its `mid`. A reader that opts in with `acceptMessageFrames` also sees a `say` message as the model writes it, on a chat whose agent talks through `say`: the text is decoded from the call's arguments as they stream (`say_text.rs`), sent as `display` frames with `partType: "message"`, frozen when chunks are lost, and withdrawn when the call isn't answered; the stored `message` part then replaces it by `callId`. Whether the chat's agent has prefrontal's `say` comes from the chat's plan as a page read last read it, since a live event can't wait for a plan read. A page read reads the plan only when its rows hold a `say` call, so on a chat whose pages hold none yet, the first one shows whole once stored. A run's end ends the live view only when it names the run that is running, since a new run's start can arrive before the previous run's end. A display `run_status`, which says the run's state changed (a provider retry starting or ending), makes the chat's watches re-read the head and leaves the live words alone: a runner that drops words it streamed sends `display_reset` for that.

Watches run in a long-held pool of handler slots, so open chats never hold up reads and sends. A route may hold at most 24 watches, which leaves room for its reads and sends; the 25th is refused `watch_capacity`.

## Sending

`session.enqueue_user_message` forwards the person's message to the runner's `session.send`. Its send id comes from the app's message id, the chat and the runner, so a retry reaches the runner under the same key and is answered with the existing send, never delivered twice. A receipt answers a repeated send for 48 hours. Modes are queue (the default), steer and interrupt, as the plan grants. Occipital never sends anything on its own and never resends after an unknown outcome.

Until a send's message is stored, Occipital follows it with `session.send_status` and lists it on every page and details reply, and on a watch that opts in, as the chat's `queuedSends` (`send_queue.rs`): `queued` while the runner holds it, `unsent` with the runner's reason when it ended undelivered, and `unknown` when the runner handed it on but can't confirm it ran. A delivered send leaves the list; the other two stay for 48 hours. The follower asks at once when the runner's `send_state.v1` event on the message bus says the send changed (see Message bus). Its timed check is a backstop: every 5 seconds while the bus reader is down, and while it is attached, once after 5 seconds (a notice can arrive before the send is followed) and then every 30 seconds.

`session.stop` cancels the running turn through the runner; `session.stop_all` asks the runner to stop everything the agent started, and reports what stopped and what kept running.

`session.promote_send` ("Send now") moves a queued message into the running turn. Occipital names the message to the runner's `session.promote` by the send id its receipt recorded; the runner decides in one step with its queue, so the message joins the turn, or has already run, and never runs twice. The send keeps its id, so its receipt and its `queuedSends` entry carry on unchanged. The session facts' `sender` carries `promote: true` when the apps may offer it: the runner declares `send_promote` for the session, and the grant includes `steer`.

## Files and images

An uploaded file goes into the model's prompt or into the session's project folder. An app that asks for the prompt gets it when the session's runner takes uploads and its model accepts the file's type; the send naming the file copies it to the runner. Otherwise the file is placed in the project and the message names its path. When the runner refuses a prompt file anyway (`media_unsupported`, `media_too_large`), the app asks Occipital to place it in the project (`upload.place`) and sends the path instead. Partial uploads wait in `upload-blobs/` and resume from the bytes already written.

How many files a message may carry follows the session's model: `session.details` reports it as `attachments` to an app that asks (images from Fusiform's `limit.images_per_request`, else 4; other files 4; each image bound the stricter of the catalog's and the runner's, the catalog's edge being the smallest of its base and `above_images` conditions), and a send naming more is refused `too_many_files` before anything is copied. Both come from one function, so the details and the send never disagree.

`session.media` reads an image a chat references: a thumbnail Occipital makes from the runner's bytes (at most 1024 pixels on the longest side, upright), or the original in pieces. Reads ask runners that support it for photo references, and those that also declare `tool_media_refs` for references to the files in tool results, so no read brings image bytes with it; an image reaches the apps as a file descriptor with its digest and size, a photo as a file part and a tool's file under its call's `media`, and its bytes only through `session.media`.

## What the model is given

`session.request_context` answers the system text and the tools of the plan in force on a session, from the runner contract's `session.plan_view`, which a runner admits as it admits `session.read`. Occipital checks the reply against the contract's closed type and passes the text, the tool schemas and the UTF-8 byte offsets on unchanged, with the members spelled the apps' way. It is the request as the plan built it, not a copy of one sent to a provider, and it holds none of Magic Context's head messages (memories, summaries, profile, docs), which the apps read from Magic Context. A runner that doesn't declare `plan_view` is refused `unsupported` without a call.

## Tool display

- **Writing:** a tool provider writes each call's record, completion and detail with `display.write` on Occipital's tool-provider route. The writer is the module the daemon attests, never a name in the body; an unverified caller is refused.
- **Pulling:** a provider may instead announce each stored record on the message bus (`display_record_ready.v1`, its id only). Occipital calls that provider's `display.read`, which answers the `display.write` params it would have pushed, and stores them with the called module as the writer, only when the daemon's catalog lists that module as daemon-verified. A pulled write is stored where the same write pushed would be, so a wake or notice record goes to the notices file (see Notices). A record that arrives both ways is stored once. Providers keep `display.write` until this path has run on them.
- **Views:** a provider with a views bucket on the message bus puts each view there, and Occipital keeps it as it arrives (see Message bus). Otherwise Occipital fetches each provider's views (`tool.views`) off the write path: when it first meets a pin, when the provider's build changes, and when a read finds the last fetch an hour old. It learns of a new build from the daemon's catalog: the daemon pushes the catalog's generation (`catalog.watch`), and Occipital reads `catalog.list` again only when that moves, at the latest after 5 minutes, or after 10 seconds while the push is down. Runner builds (which key each session's cached `role.describe`) and the modules that declare commands are read the same way. A template that fails Occipital's checks is left out, and its calls draw as a plain chip. A kept view is replaced only by a higher `template_revision` whose record schema is unchanged or has grown under the pin (same name, higher revision, every field kept); its templates are then checked with the input schema the writer serves now. A view for a `tp2` pin must name its tool, and Occipital keeps it only when that tool recomputes to the pin.
- **Joining:** a record joins a call only through a view its own writer serves for the pin the runner stored for that call. If two writers qualify, neither is served. Before it is served, a record or completion is checked against that view's record schema (`checked_body` in `display/app.rs`): a field the schema doesn't declare is dropped, since a provider may write one before the view declaring it is kept, and a body whose fields break their rules is left out, so the call draws without it.
- **Reading:** the apps read views, templates, records and details beside the pages (`display.views`, `display.template`, `session.tool_records`, `session.tool_detail`), cache them for good, and hear of new ones from `session.tool_records_watch`. Keeping them beside the pages keeps page versions the runner's alone: a record that lands after its row never reloads a chat.
- **Moved calls:** Occipital files a call under the runner that minted its key and finds it by the session and key the app asks about, so a chat moved to another runner keeps its tool rows and notices.

`display.model_names` resolves model ids to the names the apps show, from Fusiform's catalog and routing's credential-provider map (`route.catalog_targets`, on whichever module the daemon's catalog lists as providing `routing/v1`), cached for 30 minutes (60 seconds when the map couldn't be read), or until Fusiform's `catalog_changed.v1` event on the message bus. The same read takes each model's attachment limits.

## Notices

Occipital keeps each riding notice it learns of, from a page read's notices fact or the runner's live event, under its call (the runner that minted the call's key, and the key) and its sender and send id. The apps read a call's notices with `session.notices` and hear of new ones from `session.notices_watch`. A notice sent as its own message stays a chat row, marked so the apps draw it as a notice rather than the person's words.

**Wake records** say what a wake held, so the apps draw it as chips rather than the prompt text. The waking module (prefrontal) writes each record before it sends the wake, with `display.write` and `kind: "wake"`, keyed by its own send id; the sender is the route's attested writer. Occipital keeps it once per session, sender and send id, never changed. A row names its send only through the runner's read facts, so every page read records which send each message came from, in memory at once and in the file. The apps read the records of the rows they draw with `session.wake_records {messageIds}`, and a riding notice carries its send's record in `session.notices`. A row whose history moved from another session takes the one record its send has in any session, and none when two sessions hold one. There is no watch: the apps fetch a row's record before inserting the row, and a record that arrives later never replaces its plain card.

**Notice records** are the data a module writes for one of its own notices, such as AFT's notice that a background command finished, so the apps draw the notice as a card from that module's notice view rather than the folded notice text (`notices/notice_records.rs`). The module writes each one before it sends the notice, with `kind: "notice"`, pushed or pulled, keyed by its own send id, and Occipital keeps it as it keeps a wake record. It joins a row through the send the runner's read names, a riding notice through the send that notice carries, and a moved row by the same rule as a wake record. It joins only when its writer serves the view it names: the notice view key `nv1:<writer>:<name>:<version>`, built from the attested writer. Occipital keeps notice views beside the tool views, fetched with `tool.views` or put in the writer's views bucket, accepts one only from the writer its key names, and checks its templates with the record's `data` as `input` and a notice's fixed view, which has no call and no record. The apps ask for records with `acceptNoticeRecords: true`: `session.wake_records` adds `notices` by message id, and `session.notices` adds `noticeRecord`; without it both replies are unchanged. Occipital serves each record's fold `key` and folds nothing; an app shows only the latest notice per sender and key.

## Commands

A module that has commands provides `user-commands/v1` and serves `commands.describe`, `commands.preview` and `commands.run` on its management surface, admitting them only from `reserved:occipital`; the shapes are the `cortexkit-role-user-commands` crate's (`crates/occipital-module/src/commands.rs`).

- **Subjects:** a session subject names the session as its runner keys it, `{runner, harness, session}`. `session.details` serves it as `subject` to an app that asks (`commandSubject: true`), so the apps never derive it from the runner name Entorhinal records.
- **Listing:** `commands.list {subject}` merges the commands of every ready module whose manifest provides the capability, for the subject's kind (session, agent, computer, project or workspace), each named by its module. Each module's description is kept per build and read again when the module is placed on another. One whose digest doesn't match its commands is left out whole, so a broken module never hides the others; within one that matches, a command this build can't decode, one that fails its checks, or two sharing an id are left out alone, so a kind added to the contract later never hides a module's other commands.
- **Relaying:** a preview or run is checked against its command's declaration, then sent to the module with `caller`, the facts Occipital verified on the app's route (the signed desktop, its development build, or a paired device with its fingerprint). The module records them beside Occipital's principal and never treats them as authority; it confirms what needs confirming itself. The module's answer is passed on as it came.
- **Runs are never sent twice.** One sent but unanswered is reported `command_outcome_unknown`, and the app asks again under the same `request_id`, which the module answers from its stored reply.
- **Nothing enters a chat.** A run is the person's action, never part of a transcript or of what a model reads.

## Moving an agent

When Entorhinal moves an agent to another computer, its chats keep their display data there: Occipital is a participant in the move (`moves.rs`), on the `agent-data` internal service, answering only `reserved:entorhinal`. It takes the whole agent as its one ref (kind `agent`), never a runner's session kind, since covering one is what makes a move admissible and Occipital can't carry a conversation.

- **What travels:** for the sessions the cut moves (Entorhinal's `agent.move_refs`, each ref mapped with `agent.session_for_ref`), their call pins, the tool records, completions and details of those calls, riding notices, wake and notice records, the map from message to send, and queued and unsent sends (`moves/rows.rs`). Every row is keyed the same on any computer, so a row is copied whole. A receiver whose build doesn't know a table in the stream refuses it, so no rows are dropped on the way.
- **The stream:** the rows go as one JSON-lines stream (`moves/payload.rs`, format `occipital-chat-display/v1`) through Engram's session door, under a handle fresh for each cut. An agent with no rows here carries no stream.
- **Source:** `prepare` holds new sends to the moved sessions, waits up to 30 seconds for sends already past the hold to finish writing their rows (refusing retryably if they don't), then reads the rows, writes the stream and admits it; `export` checks the door holds it; `release` drops the waiting sends the stream carries, which the new computer follows now, and keeps holding the sessions as living there; their display rows stay, so a record a provider writes after the cut is kept for a move back. `abort` lifts the hold.
- **Receiver:** `import` reads the stream back with the cut's id and checks its digest, refusing any line over 16 MiB; `activate` records that it has started, then inserts the rows in batches without replacing any row already held, except that a call's pin and a riding notice follow the session the incoming history files them under. It lifts any hold an earlier move away left on the agent. An activation cut short by a failed write is finished by the next `activate`, never aborted.
- **Ops:** an op takes its cut's lock, then its agent's, so one slow move never holds up another agent's; `status` takes none.
- **Held sends:** a send to a held session never reaches the runner. It is refused `session_moving` while the agent moves, and `session_held_elsewhere` once it has moved, naming the new computer as `holder` when the release named its box id (`holderBox`, agent-data 0.3.3) and naming none otherwise; the release's own `holder` is a pseudonym, never shown. A runner that let a moved session go refuses a send with its own `session_held_elsewhere`, which reaches the apps the same way. A send answered before the move keeps its receipt.
- **State:** each cut's step is a versioned file in `moves/` (`moves/state.rs`), synced before an op replies, so a restart never lets a send land past a cut; the holds are worked out from those files, ordered by a sequence the module counts, never by the clock. A file it can't read stops sends (`provider_unavailable`) and marks health `failing`, while reads go on. A build that first meets unversioned files keeps their bytes in `moves/pre-v2/` before rewriting them, so rolling back to an older build means restoring those copies.

## Reply teaching and the interface language

The language library parses, checks, evaluates and lays out the closed interface language: the tags a head's reply may hold, `show_ui` programs and tool templates. It has no panic paths, because apps embed it. Its catalogs are pinned by publication digest. Until the apps' first release a catalog changes in place, with no aliases: a reply stamped with an earlier digest doesn't draw as rich content (the apps show its readable text instead), and a tool template naming one is refused, so its calls draw as plain chips. Replies no longer hold `Table` (`show_ui` programs and tool pages still may): a reply's `<Table>` now fails as any refused tag does, and in the readable text an older reply's table with written rows reads as its rows, one line each.

- **Reply teaching:** asked for its system text, the module answers with teaching generated from the catalog, plus the stamp a runner records on each reply. The catalog's teaching section is outside its digest, so rewording what models are told changes no stamp.
- **Tool templates:** a row template reads the call's view (its record, completion and timing) and the clock only inside a fixed-size `Slot`, or in a prop that only colours (`ToolHeader`'s `failed`), so a row's height never changes when they arrive. `occipital-check` gives tool providers the same checks in their CI.
- **The phone:** `crates/occipital-ffi` exposes the library as a C interface that turns any panic into a status code, built into `ports/swift/OccipitalCore.xcframework`; `OccipitalKit` wraps it in Swift.
- **Facts:** `format_fact` words a command preview's or result's facts ("about 18k tokens", "Building, 40%") and gives each a tone, so both apps draw them alike; a fact's value is never the module's own text.
- **Schedules:** `format_schedule` words a module's recurring schedule ("Every day at 03:00", "Mondays and Thursdays at 09:30") in the person's own clock. The app passes the minutes between its zone and the schedule's, since the library carries no zone rules; a cron-only schedule is refused, and each app draws its own fallback.
- **Links and chips:** `crates/occipital-refs` finds "Issue N", "PR #N" and `owner/repo#N` mentions in text and returns byte ranges with URLs, built from the repository named in the project record prefrontal serves beside each agent, and `@NAME` mentions with the name, which the apps look up among the agents they know. The apps draw the links and chips; the text is never changed.

## Storage

All stores sit in Occipital's data folder, normally `<data home>/cortexkit/occipital/`, named by the daemon in HELLO_ACK.

| File | Holds | Backed up |
|---|---|---|
| `store.db` | native `show_ui` records, send receipts, held sends, the state of uploads in progress | yes |
| `display.db` | tool records, completions, views, call pins | yes |
| `display-details.db` | tool details (large, may hold file contents) | no |
| `notices.db` | riding notices, wake and notice records, the send each read message came from | yes |
| `upload-blobs/` | partial upload contents | no |
| `moves/` | each agent move's step, and its stream while the move needs it | no |

- **One writer:** `store.db` is opened with cortexkit-store, which holds a single-writer lease; every write is fenced.
- **Migrations only move forward.** Each file, and each table group in `store.db`, has its own version, and a binary refuses to start on one ahead of what it knows. So a build that adds a migration makes rollback a store step, not a plain binary swap: copy the changed files aside before placing it.
- **Backups:** at every start the module writes `engram-catalog.json`, so Engram backs up the files marked yes, live.
- **Restores are safe:** an older restored copy never makes Occipital resend: sends are deduplicated by the runner, and uploads resume.

## Message bus

Occipital reads one durable on the local message bus (ck-bus, NATS), `m_occipital`, and publishes nothing (`bus.rs`). Each event is only a wake, and the fact is read again through the call that owns it:

- a runner's `send_state.v1.occipital` makes that send's follower ask `session.send_status` at once;
- Fusiform's `catalog_changed.v1` makes the model names held old;
- a tool provider's `display_record_ready.v1` names a record it stored, which Occipital reads back with `display.read` (`display/pull.rs`; see Tool display).

It also watches each tool provider's `views` bucket that bus naming declares it a reader of (AFT's and Cerebellum's). The key is the lowercase hex of a schema pin, the value the provider's `tool.views` answer for it, and Occipital keeps each put view through the same checks as a fetched one, without asking. While the watch is open or opening, a pin with a view already kept is never fetched again, not even after the provider's build changes, since the provider puts every pin it serves and puts it again when its answer changes. A bucket deleted and made again (a manual repair) keeps what is kept: the watch reads the new bucket's entries through the same checks. A pin with nothing kept is still fetched with `tool.views`, and while the watch is down kept views fall due as for any provider.

A send-state or catalog event is acknowledged once its wake is handed on. A record event is acknowledged once its record is stored or refused for good, and delivered again 30 seconds later when the provider or the display store can't be reached. One that can never be read is terminated. The timed checks stay as backstops, so a bus that is down only slows these updates.

## Failure handling

- **Health** comes from in-memory counters only, never a store or network read, and reports `failing` naming any background task that stopped. Its metrics carry the message bus reader's counts (`bus`): whether it is attached, whether its connection is up (a reader stays attached while the client replaces a lost connection), the wakes it handled by kind, records stored, refused and retried, views served, events it couldn't read, and deliveries the bus client dropped unread because they weren't from Occipital's own durable or watches (`foreignDropped`, which should stay 0). Those wakes are logged at debug only, so the counts are how an operator sees them arrive.
- **Runner refusals are mapped, never passed raw.** A read the runner refuses reaches the apps as `cursor_expired` or `session_unknown` when that is what it says, as `session_held_elsewhere` (naming the new computer as `holder` when the runner does) for a session whose agent moved to another computer, and otherwise as `provider_unavailable`, which the apps retry; the runner's code stays in the message. A media read keeps `unknown_media` and `invalid_params`, and a plan view `no_plan` and `too_large`, which are final. A plan view the runner refuses `transient` with `detail.cause: "awaiting_plan_applied"` reaches the apps as `context_not_ready`: the runner serves it from the session's next applied plan, so the app reads again later instead of retrying. A send's refusal reaches the apps under a send code (`enqueue_not_authorized`, `client_message_id_conflict`, `media_unsupported`, `media_too_large` and others) or as `runner_refused`, with the runner's code, whether the same send may succeed later, and how long to wait first. A send to a chat its owner released, which the runner deletes soon, is refused `session_released`, with the earliest deletion time as `deleteAfterMs` when the runner names it. The contract lets a later send start the session afresh, but for a person's send that would be an empty chat under the old name, so it is final: the app keeps the draft and says the chat is ending. A wait (the account that would serve the send is at its usage limit, routing can't choose an account yet, or routing has no free capacity) counts as one that may succeed later, after the wait the runner names; it is never reported as failed. When `session.head` names the code the session's last run ended with, the session facts carry it as `lastRun.error.providerCode`, if it is one of the codes the runner contract names, so the apps can say a run ended on an account wait. When the head says what the run waits on, the session facts carry it as `lastRun.awaits` (who ends the wait, why, and when it moves or gives up); its quoted `message` passes with `from` naming whose words they are (runner, sign-in plugin, host or provider; the apps open it on tap, never in the line), is left out when `from` is a source the contract doesn't name, and an `awaits` that doesn't decode is left out rather than failing the read. A queued send whose turn ended in an error, or that the runner never got to its host or past routing (`not_delivered`, with the runner's reason), is listed unsent with that run's code (`runnerCode`, read once from `run.status`) and, for a wait, `retryAfterMs` from `endedAtMs`; the app sends the words again as a new message, since the runner answers the old send id with its final record. A send the host refused for good (reason `host_refused`) also carries the run error's `cause` when it is one the contract names (an unreadable attachment, an invalid host configuration, an unsupported host version, a managed policy), since sending the same words again can't succeed until the person changes something. A send the runner handed on but can't confirm ran (`delivered.as: unknown`) is listed `unknown`, never as delivered, and is never sent again, since a repeat could run it twice.
- **Mutations are never retried blindly.** A send, Stop or command run whose outcome is unknown is reported, not resent; the app's retry carries the same key.
- **Logs** record every app request with its method, session, outcome and the calls it made: a send, Stop, Stop everything, Send now, command run or finished, aborted or placed upload at INFO, and a transcript or display watch's opening, any other success at debug level unless it took over 2 seconds, and refusals and deadlines as warnings. A request other than a watch that is still running after 10 seconds gets one extra warning naming its current step. Each watch that ran also logs its end at INFO: which device it served (`desktop`, or the device class and the start of its pairing fingerprint, such as `phone:baa6a4f7`), how long it was open, how it ended (the app cancelled it, the app's connection closed, its stream ended or was refused), how many notices it sent, with those that only changed the chat's list of waiting messages counted apart, and, for a display watch, which frames it asked for and how many of each it sent; for a transcript watch, whether it asked for `heldCopy` (the id naming which copy of the chat that app holds, so its claims are checked against its own copy), whether its claim named one, and which view it read. A watch refused before it opened is logged as a warning with its device and code. Each send added to a chat's waiting list, and each one settled (delivered, unsent with its reason, or unknown), is logged at INFO with the app's message id. Message text and file names never reach the log.

## How changes are verified

- **Sample sets:** every wire shape the apps decode is pinned by a tagged sample set with SHA256SUMS, under `crates/occipital-app-reader/test-vectors/` (and the FFI and refs vectors). The apps pin those tags, so a wire change ships as a new tagged set and the old one stays frozen.
- **Runner recordings:** runners' own recorded replies are copied byte for byte into the module's test data and served through Occipital's real handlers.
- **Break checks:** a fix is proven by breaking it on purpose and watching its test fail.
- **The phone library** is rebuilt reproducibly on the build server, and `scripts/check.sh` refuses a committed library that no longer matches its sources.
