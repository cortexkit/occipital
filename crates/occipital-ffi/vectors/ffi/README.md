# occipital-ffi round-trip vectors

Generated by `crates/occipital-ffi/src/vectors.rs`; do not edit by hand.
`SHA256SUMS` lists the SHA-256 of every other file here
(`sha256sum -c SHA256SUMS`). Run the crate's tests with
`OCCIPITAL_BLESS_VECTORS=1` to regenerate them; without it a test fails if
regenerating would change any byte.

Each `*.json` file is one case:

    {"entry": "<entry point>", "request": {...}, "status": <int32>, "response": ...}

Replaying a case means calling `entry` with the arguments in `request` and
checking that it returns `status` and leaves `response` in `*out`:

- A member named after a JSON parameter (`ctx_json`, `layout_json`,
  `tree_json`, `path_json`, `records_json`, `event_json`) holds the exact
  string to pass.
- A member named after a byte buffer (`src`, `bytes`, `tail`, `text`) holds the
  bytes as standard base64; pass the decoded bytes and their length.
- `"metrics": "fixed"` means an `OccMetrics` table whose `l` and `t` return
  20 for every input and whose `tw` returns the UTF-8 byte length of its
  text, the metrics the golden traces measure with.
- `response` is the exact string left in `*out` (compare byte for byte), or
  `null` when `*out` is NULL.

A case whose entry is `occ_reply_new` is a whole reply session. Its request
is `{"stamp_json", "layout_json", "chat": 0, "app": 1}`: `chat` and `app`
are the scopes of fresh accounts made with `occ_account_new` for this
session. Its status is that of `occ_reply_new`, and its response is the list
of calls then made on the session handle, in order, each an object of the
same four members with the handle argument left out. Free the session with
`occ_reply_free` after the last call.

The cases are the inputs of every golden trace of occipital-lang that these
entry points can reach: the §16.8–§16.11 replies, streamed one byte per
`occ_reply_chunk` call and finished in one call, with their snapshot events
and measurements; `occ_program_check` on every §16.1–§16.7 program case and
on the reserved-write programs; the reserved-write replies; and
`occ_measure_tree` and `occ_measure_block` on the reply trees. Two more
`occ_program_check` cases cover a program with error diagnostics and a
source with invalid UTF-8; both return `OCC_OK` with the diagnostics in the
result. The scheduler traces drive a program session, which this library
does not expose, so they have no vectors.

The `template-bash-row-*` cases evaluate a tool row with
`occ_template_evaluate`: a command far wider than the row, then a short Slot
for its outcome, once while the outcome is still to come (`waiting`) and once
with it (`filled`). Each `measure-tree-bash-row-*` case measures that tree as
a 200-wide transcript row: the Slot keeps its width, the command is cut to
what the Slot leaves, and both trees have the same height.

The `version` case is `occ_version` with no arguments; its request is `{}`.

The `text-references` case is `occ_text_references` on a reply naming an
issue, a pull request in another repository, a pull request inside a code
span and an agent, under a project record as core serves it. The rules
themselves are pinned by the `text-references-v2` vectors of
cortexkit-occipital-refs;
this case pins the entry point's JSON.

The `format-fact-*` cases are `occ_format_fact` on one fact each: a number
with a unit and `approx`, a state with progress, and a fact the rules refuse,
which answers its code.

The `format-schedule-*` cases are `occ_format_schedule` on one schedule each,
with `shift_minutes` the integer to pass: a weekly schedule in its own zone,
the same schedule an hour east (its day moves past midnight), an hourly one,
and a cron-only one, which answers its code.
